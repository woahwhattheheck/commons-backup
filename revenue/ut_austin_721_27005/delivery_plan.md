# Bounded delivery plan — UX strategy support + implementation acceptance

This plan is written so it can become either (a) part of a truthful prime response once every prime gate is evidenced, or (b) a paid specialist workshare to a qualified digital-design prime.

## Phase 0 — evidence and stakeholder contract

Inputs: University-provided goals, existing site inventory, analytics, brand/design standards, stakeholder roster, current Drupal/component constraints, accessibility baseline, known integrations, search/discovery baseline.

Outputs:
- source/decision register with owner and freshness;
- stakeholder/review cadence;
- scope and exclusion ledger;
- acceptance matrix that separates recommendation, design artifact, implementation guidance, and University-controlled production decision.

Acceptance: every recommendation names its evidence and owner; unresolved or contradictory inputs are HOLD, never silently assumed.

## Phase 1 — discovery, IA, and UX strategy

Work:
- audience/task inventory and top-journey hypotheses;
- content-domain and IA model;
- search/discovery requirements;
- analytics-informed hypothesis register;
- accessibility/inclusive-design constraints captured before visual design.

Acceptance:
- each key user journey maps to a measurable outcome;
- IA nodes have explicit ownership/content dependency;
- search requirements identify indexable source, query intent, result behavior, empty/error states, and accessibility expectations;
- research assumptions are labeled where direct University user evidence is not yet supplied.

## Phase 2 — design system and implementation-ready specifications

Work:
- component/state inventory;
- token/variant naming;
- responsive behavior;
- keyboard/focus/error/empty/loading states;
- implementation annotations for Drupal/component integration;
- content/model dependencies.

Acceptance:
- all interactive components specify keyboard and focus behavior;
- every component has default/empty/loading/error/disabled states where applicable;
- specifications distinguish invariant design intent from implementation suggestion;
- artifact is traceable to source requirement / decision.

## Phase 3 — technical planning and implementation support

Work:
- component-to-Drupal mapping;
- integration and migration risk register;
- URL/redirect/search-index transition plan;
- analytics/instrumentation acceptance;
- release/rollback acceptance plan.

Acceptance:
- no production credentials or deployment authority required for review;
- build artifacts can be evaluated against immutable acceptance fixtures;
- redirect/search/analytics requirements have deterministic sample checks;
- rollback criteria are stated before launch.

## Phase 4 — QA, accessibility, and technical validation

Evidence surfaces:
- WCAG-oriented keyboard/focus/name/role/state checklist;
- responsive and content-stress matrix;
- semantic-HTML/component contract review;
- search/discovery behavior fixtures;
- broken-link/redirect sample verification;
- immutable artifact digest + review receipt.

Acceptance packet:
1. exact artifact/version under review;
2. requirements covered;
3. pass/fail/hold per criterion;
4. defects with reproducer and evidence;
5. residual risks / University decisions;
6. re-test delta;
7. no claim of production acceptance until University owner accepts.

## Optional complementary workshare

A qualified prime can retain strategy, creative direction, research, portfolio/reference claims, staffing commitments, commercial terms, and buyer relationship while TJLabs supplies a bounded **implementation acceptance / accessibility / technical-validation** workshare.

Suggested commercial structure is intentionally **not priced in this carrier**. Pricing requires owner authority and must be reconciled with the solicitation BidTables or a prime subcontract structure before any external send.

## Explicit exclusions

No full production implementation, hosting, long-term support, content ownership/migration, production AI chatbot/search implementation, third-party platform procurement, or buyer-controlled deployment decision is implied.
