# UIOWA-078 — AI workflow benefit and operating-cost kit

**Working offline preparation tool; all checked-in cases are fictional.** This is
not a finding about the University of Iowa, a product-price comparison, a spending
authorization, a savings forecast, or the engagement's assessment compiler.

The kit follows a task through context preparation, generation, verification,
repair/manual fallback, integration, recurring support and maintenance. It returns
staff capacity, loaded-labor opportunity value and a separate cash-conversion
scenario. It does not assume that faster generation means successful delivery.

## Run the complete example

Python 3.10+ syntax; actually exercised with Python 3.13.5 on Linux. No third-party
packages, network access, model calls, API keys, spreadsheet application or full
Commons checkout are needed. Copy this directory as a unit, then run:

```sh
python rehearse.py --out /tmp/uiowa-078-example
python -m unittest -v test_economics.py test_rehearse.py
python -O -m unittest -v test_economics.py test_rehearse.py
```

The first command generates the fictional input and seven outputs, then checks
every generated byte against the version-bound example manifest. Its output
names the actual checked files and scenario classifications. Use a fresh output
directory; the command replaces its own named output files on subsequent runs.
It does not delete unrelated files.

For an edited assumptions document, the supported calculator entry point is:

```sh
python synthetic_cases.py > /tmp/ai-economics-input.json
python economics.py /tmp/ai-economics-input.json --out /tmp/ai-economics-result
```

`rehearse.py` is the fixed example acceptance path; `economics.py` is the reusable
calculator. The latter intentionally does not require edited assumptions to match
the synthetic example's digest. A malformed input returns exit code 2 and a named
error. Unknown measurements are valid data and remain visibly UNKNOWN.

## What an operator receives

| File | Purpose and interpretation |
|---|---|
| `report.json` | Full machine-readable base results, range endpoints with replayable input witnesses, break-even calculations, one-at-a-time sensitivities and missing-input diagnostics. Decimal values are strings; unknowns are null. |
| `report.md` | Readable scenario comparison, thresholds and first six measurement priorities per case. The CSV/JSON contains the full measurement plan. |
| `summary.csv` | One row per scenario, with currency, horizon, input/result basis, economic range, cash-conversion base and net capacity hours. |
| `input_register.csv` | Editable collection worksheet: all 16 inputs, units, low/base/high assumptions, evidence basis, source and collection question. |
| `sensitivity.csv` | One input varied at a time, all other inputs fixed at base; signed endpoint results and absolute economic swing. |
| `measurement_plan.csv` | Missing measurements first, then variable assumptions ordered by economic swing. Cash conversion can be cash-important even with zero economic swing. |
| `volume_checking_grid.csv` | Nine combinations of low/base/high volume and verification effort, holding other inputs at base. |

Checked-in `example/report.md` and `example/summary.csv` are actual sample outputs.
The other reports are deterministically regenerated, not withheld session-only
work. `example/expected-output-sha256.json` records all output byte digests plus the
input digest. `verification.json` records the executed test scope.

## Version 1.0 input contract

The top-level JSON object has exactly `schema_version`, `input_basis`, `currency`,
`horizon_months` and `scenarios`. `schema_version` is `"1.0"`; horizon is a positive
integer; currency is three uppercase letters and is used consistently throughout
one document. No exchange-rate conversion occurs.

Each scenario has exactly `id`, `group`, `label`, `notes` and `inputs`. IDs are unique
and use letters, digits, dot, underscore or hyphen. Group is an organizational
context label, not a maturity score. The example uses fictional ESS/RIS/IAM cases.
Every input cell has exactly these four fields:

```json
{
  "range": {"low": "5", "base": "7", "high": "10"},
  "unit": "minutes/assisted task",
  "basis": "synthetic",
  "source": "synthetic_cases.py::SYN-ESS-DOCS::checking_minutes"
}
```

For an unknown input, use `range: null`, `basis: "unknown"` and a source explaining
what remains to collect. There is no silent zero, point estimate, missing-column
fill or numerical imputation. All 16 keys remain present. Decimal strings or
integers are accepted, with `0 <= low <= base <= high`. Binary JSON floats,
booleans as numbers, non-finite numbers and duplicate JSON keys are rejected.
Fractions must be in [0,1]. Explicit zero is different from unknown.

| Input | Exact unit | Accounting boundary |
|---|---|---|
| `monthly_tasks` | tasks/month | Comparable eligible task volume; not just successful generations. |
| `adoption_fraction` | fraction | Share actually attempted with assistance. |
| `baseline_minutes` | minutes/task | Current workflow through accepted output. |
| `author_minutes` | minutes/assisted task | Context preparation, prompting and initial editing. |
| `checking_minutes` | minutes/assisted task | Verification of all attempted outputs, including discarded ones. |
| `rework_fraction` | fraction | Fraction requiring additional repair or manual fallback. |
| `rework_minutes` | minutes/reworked task | Additional time conditional on rework. |
| `attempts_per_task` | generation attempts/task | All billable attempts, including retries. |
| `generation_cash_per_attempt` | currency/attempt | Incremental generation cash, with dated assumptions or measurements. |
| `loaded_hourly_rate` | currency/hour | Aggregate capacity valuation, not individual productivity. |
| `integration_hours` | hours one-time | Initial integration, evaluation, training and rollout effort. |
| `setup_cash` | currency one-time | External setup cash excluding already-valued integration labor. |
| `support_hours` | hours/month | Recurring support, excluding per-task repair. |
| `maintenance_hours` | hours/month | Updates, evaluation refresh and knowledge maintenance. |
| `platform_cash` | currency/month | Incremental fixed recurring cash, excluding generation charges. |
| `cash_conversion_fraction` | fraction | Signed capacity value expected to change actual labor cash. |

`input_basis` is `SYNTHETIC`, `PLANNING_ASSUMPTIONS` or `MEASURED_INPUTS`. Cell basis
is `synthetic`, `assumed`, `observed` or `unknown`. A synthetic document cannot
contain observed/assumed cells; a measured-input document cannot relabel
synthetic/assumed cells. These labels record the supplied basis, not verification
that a source is authentic. Even measured inputs produce `MODELED_NOT_OBSERVED`
results: extrapolation is not an observed outcome.

## Equations, units and sign conventions

Let H be horizon months, N monthly tasks, a adoption fraction, b baseline minutes,
d author minutes, c checking minutes, p rework fraction, r conditional rework
minutes, w loaded hourly rate, I integration hours, S setup cash, U monthly support
hours, M monthly maintenance hours, F monthly platform cash, t attempts/task,
g cash/attempt, and z cash-conversion fraction.

```text
A = N*a                                      assisted tasks/month
B = A*b/60                                   baseline hours/month
L = A*(d+c+p*r)/60                            assisted task hours/month
K = B-L-U-M                                  net capacity hours/month
K_H = H*K-I                                  net capacity hours over horizon
C = A*t*g+F                                  external cash/month
C_H = H*C+S                                  external cash over horizon
E_setup = I*w+S                              one-time economic cost
E_month = K*w-C                              recurring economic net/month
E_H = H*E_month-E_setup = K_H*w-C_H            horizon economic net
Cash_H = K_H*w*z-C_H                          separate cash-conversion scenario
```

Positive K_H means potentially reusable staff capacity; negative means additional
staff effort. Positive E_H is opportunity value after external cash, not cash
saved. Positive Cash_H depends on the specified actual cash-conversion mechanism.
At z=0, Cash_H=-C_H even if E_H is strongly positive. At z=1, Cash_H=E_H.
The signed conversion is a simplifying assumption, not evidence of layoffs,
contractor reduction or new hiring. Negative capacity still needs staffing and
service-feasibility assessment even when no additional labor cash is modeled.

Unassisted tasks cancel from this incremental comparison; do not subtract them a
second time. Shared integration or platform costs belong in one attributed
scenario or an explicit allocation, not in every scenario and then again in a
portfolio total. This version does not aggregate a portfolio or resolve shared
cost attribution. Never count the same review minute in author, checking and
rework, or the same labor cost in loaded effort and external cash.

### Break-even analysis

Per-assisted-task economic margin is `u=(b-d-c-p*r)*w/60-t*g`. Fixed recurring
economic cost is `f=(U+M)*w+F`. For positive u, the assisted tasks/month required
to recover costs over H months is `(f+E_setup/H)/u`. The report also provides the
whole-task ceiling, required adoption at base volume and whether that adoption
is at most one. A negative unit margin cannot be fixed merely by increasing
volume. Undefined or unattainable thresholds are not called a successful pilot.

For A>0 and w>0, the maximum checking minutes at the given volume is:

```text
c_max = b-d-p*r - (60/w)*(t*g + (f+E_setup/H)/A)
```

A negative c_max means even zero verification effort cannot break even under
those assumptions; it is not a recommendation to skip necessary checks. Simple
payback is E_setup/E_month when recurring net is positive. This is undiscounted
steady-state payback, not cash payback or a guaranteed completion date.

## Range and sensitivity method

Low/base/high are user-supplied bounds, not probabilities, percentiles or standard
errors. The base is not automatically the mean or median. The economic and cash
formulas are multi-affine in the inputs. Every cost coordinate is non-increasing
and baseline time is non-decreasing in either net objective. Volume, adoption,
loaded rate and cash conversion can reverse direction. The algorithm enumerates
their endpoint combinations at both monotone directions (at most 32 evaluations)
and retains a full input witness for each resulting minimum and maximum.

The method covers the independent rectangular input domain. Correlated or
infeasible joint assumptions can make those bounds too broad. Use coherent
separate scenarios when real constraints connect inputs; do not interpret a
mathematically feasible corner as a likely operating state. One-at-a-time
sensitivities and the nine-cell grid are additional views, not replacements for
the joint envelope. Tests compare the optimized method with all 65,536 endpoints
of one 16-input case and exhaustive subsets of twelve seeded adverse cases.

Calculations use Python Decimal with 50 significant digits and no intermediate
cents rounding. Repeating division is still finite-precision; this is not exact
rational arithmetic. JSON keeps decimal strings; Markdown rounds for display to
two decimal places. Very close threshold decisions require appropriate input
precision and review, not reliance on display rounding.

## Measurement and decision rehearsal

Start with a comparable accepted-output definition and task mix, then record
baseline and assisted end-to-end time using the same scope. Keep failed,
abandoned and repaired attempts in the denominator. Collect verification and
conditional repair separately. Establish observation windows and distinguish
ongoing support from one-time rollout. Retain source versions, dates and inclusion
rules. Ask the responsible organizational role to explain whether capacity can
actually change cash expenditure; do not substitute the loaded labor rate for
that answer.

Use the generated measurement plan to select the largest uncertainty worth
reducing. Re-run with revised evidence, compare input hashes and scenario IDs,
and retain the old and new assumptions. Economic attractiveness is only one
input: use the existing evaluation, coding-workflow and lifecycle components for
quality, usefulness, maintainability and support evidence. Equal output quality,
steady volume and stable task mix are modeling assumptions until evidenced.

Remaining real inputs include task definitions and counts, end-to-end effort,
repair incidence, metered usage, aggregate labor valuation, rollout effort,
ongoing maintenance and an explicit cash-conversion rationale. No real University
records belong in this public repository; use the agreed engagement evidence
handling arrangements instead.

## Integration seam and limitations

The command-line JSON contract is the stable seam for UIOWA-098/100/101 and the
independent ORBIT-27 workbook/oracle carrier. `component.json` describes it.
Preserve `input_basis`, `result_basis`, currency, horizon, missing inputs and both
input/model digests in downstream records. Do not map POSITIVE_ACROSS_RANGE to a
maturity score, approved investment or completed improvement. The model does not
replace the existing workshare/compiler or write to the workbench.

CSV protects formula-like user text by prefixing an apostrophe while preserving
negative numeric values. JSON is the lossless interchange representation; do not
round-trip protected CSV text as though it were byte-identical to source text.
The CLI writes only its named outputs but is not a transaction across all seven
files on an I/O failure. Retain the source document and rerun into a fresh folder
when an export is interrupted.

Not modeled: discounting, tax, inflation, seasonal demand, adoption ramp,
queueing/concurrency, different role rates, long-term quality value, displaced
business demand or shared-cost allocation. No observed benefits, peer percentile,
individual performance score, product purchase or commercial commitment is
created by this kit.
