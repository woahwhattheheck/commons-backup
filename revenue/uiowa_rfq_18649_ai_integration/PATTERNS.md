# Reference patterns and integration decision worksheet

All systems and observation records below are fictional. These are architecture options, not commercial product recommendations, University findings or running model integrations. The executable comparison is generated by `example_cases.py` and evaluated by `assess.py`.

## 1. Synchronous assistance

A caller supplies a bounded task and source references, an adapter requests a draft, output checks run, and a human sees the result. The existing transaction should be considered separately: waiting on an optional draft can unintentionally make generation a new critical dependency.

**Suitable conditions:** the complete response envelope fits the interactive budget; the data movement is understood; the source and response contract are versioned; there is a usable non-AI behavior. **Tradeoffs:** simplest immediate experience, but generation latency and outages are visible to the caller; embedded provider-specific request fields increase migration work. **Effort:** adapter, output checks, replay cases, timeout/degraded behavior, support instructions and operator training. **Evidence still needed:** a representative end-to-end trace, dependency observation window, payload/retention inventory, retained core-continuity exercise and replacement-adapter comparison.

The fictional SYNC design intentionally blocks the original change flow, sends its excerpt to an unspecified external zone, and has no retained migration exercise. The tool surfaces those weaknesses instead of rewarding its apparently simple interface.

## 2. Asynchronous job

The application accepts a versioned job envelope and exposes a job identifier/status. A worker obtains the bounded source input, requests a draft, records the result and presents it for human review. Ordinary work can continue independently. Acknowledgement, completed draft and reviewed outcome are distinct milestones.

**Suitable conditions:** a delayed result is useful and the owner agrees a completion expectation. **Tradeoffs:** less coupling to generation on the response path, but queue wait, duplicate deliveries, cancellation, progress visibility, retention cleanup and support work must be designed. An available queue acknowledgement says nothing about whether a draft eventually completes correctly. **Effort:** versioned job envelope, duplicate-result handling, status/result interface, stale-job handling, replay/fallback exercises and support training. **Evidence still needed:** submission-to-completion timings including human waits, queue behavior during generation failure, job/source version linkage and retained migration/replay observations.

The fictional ASYNC design has a 90–250 ms acknowledgement envelope and a 61,990–316,250 ms submission-to-reviewed-result envelope. These are authored scenario ranges, not measured infrastructure performance. The first application's 30-minute completion budget is compatible with those assumptions. In the knowledge-assistant case the completion budget is unknown and source citations are missing, so the same pattern is not automatically suitable everywhere.

## 3. Retrieval-assisted drafting

A maintained source collection provides versioned excerpts through a retrieval adapter. The draft includes source locators, and a human checks both the answer and its support. The index/retrieval configuration, source versions and generation adapter form separate maintenance and portability responsibilities.

**Suitable conditions:** a useful result needs supported statements from an owned, maintained collection. **Tradeoffs:** citation capability comes with source freshness, index lifecycle, retrieval evaluation and replay work. Exporting source text does not demonstrate equivalent retrieved sets or answer behavior after an index/embedding change. **Effort:** retrieval/draft interfaces, source-version and citation mapping, source freshness ownership, export/rebuild rehearsal, answer-support replay and support training. **Evidence still needed:** the actual collection/version inventory, freshness expectations, support ownership, retained export/rebuild comparison, latency path and data movement.

The fictional RETRIEVAL option adds source citations. It also has unknown export/rebuild evidence and a maintenance range that overlaps the research-support team's assumed capacity. The worksheet keeps that tradeoff visible instead of turning the capability match into a blanket approval.

## Common request/result contract to inspect

The following is a design example only; no endpoint is implemented or called by this kit.

```json
{
  "contract_version": "draft-request.v1",
  "request_id": "SYN-REQ-001",
  "recommendation_id": "SYN-REC-080-A",
  "task": "draft_change_summary",
  "source_refs": [{"artifact_id": "SYN-CHANGE-7", "version": "v2", "locator": "description"}],
  "output_contract": "reviewable-draft.v1"
}
```

```json
{
  "contract_version": "reviewable-draft.v1",
  "request_id": "SYN-REQ-001",
  "status": "needs_review",
  "draft_ref": "SYN-DRAFT-7-v1",
  "source_refs": [{"artifact_id": "SYN-CHANGE-7", "version": "v2", "locator": "description"}],
  "workflow_version": "SYN-WORKFLOW-v3",
  "review_required": true
}
```

Inspect error/unavailable/pending states as well as success. Ask how callers distinguish an accepted job, a generated draft, a rejected/unusable output and a reviewed outcome. Inspect whether retries and repeated job events create multiple conflicting results. Preserve source and contract versions across export/import and adapter change. These are engineering questions, not a claim that a generic envelope makes every provider interchangeable.

## Fictional observation records

`SYN-PORT` represents an **authored fictional retained observation** for the ASYNC fixture: a replacement adapter accepted the same versioned envelope; the draft/result and source-reference fields survived export; the toy replay set was described as retaining expected statuses; the core support instructions were described as updated. No actual service, provider swap or model replay was executed. This record intentionally exercises the `demonstrated` state in a document whose top-level `synthetic` flag is true. An actual engagement must substitute retained artifacts and observations before using that state as evidence.

`SYN-FALLBACK` represents an **authored fictional retained observation**: generation was described as unavailable while ordinary human-operated changes continued; pending drafts stayed visible and were not relabeled complete. This is not a live failure-injection receipt. The executable tests exercise the assessor's interpretation of this record; they do not test deployed core-workflow continuity.

The other synthetic reference locators identify the authored timing envelopes, movement inventory and effort ranges in the generated fixture. The input-byte hash binds each report to the exact supplied version. That binding proves which bytes were assessed, not that the scenario assumptions are true.
