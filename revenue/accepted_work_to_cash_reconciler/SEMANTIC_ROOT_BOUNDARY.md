# Accepted-work-to-cash semantic-root boundary

The reconciler composes the merged `revenue_funnel_control` generation and then adds a narrower owner-action layer. The upstream compiler/verifier identities, source-class policy sets, and the rest of the imported engine generation are therefore authority-bearing code, not caller policy.

## Ordinary module rebinding

Package bootstrap installs a loader wrapper for the exact `revenue.accepted_work_to_cash_reconciler.engine` module before that module executes. After normal module execution completes, the exact module object is converted to a sealed module type. Existing engine globals cannot then be assigned or deleted through ordinary module attribute operations. This includes the upstream compiler/verifier aliases, route and external-acceptance class sets, public compile/verify functions, and their semantic helpers.

The upstream trust root is protected before downstream capture as well. `revenue.revenue_funnel_control` now installs its own lazy loader wrapper before `revenue.revenue_funnel_control.engine` executes. On every normal engine import the loaded upstream module object is sealed after source execution, so existing exports such as `compile_bundle`, `verify_bundle`, and `_make_core` cannot be reassigned or deleted and then captured by a later first import of the reconciler. This closes the pre-import poisoning predecessor from review `5233132461`; moving the fake one symbol sideways to the upstream factory is blocked by the same module-generation seal.

Both packages remain lazy: importing a package alone does not import its engine. Direct submodule import is sealed before control returns to caller code. `python -m revenue.accepted_work_to_cash_reconciler.engine` and `python -m revenue.revenue_funnel_control.engine` continue through their normal code-loading paths without eager-package-import warnings. Ordinary `importlib.reload(engine)` remains supported for normally imported module objects; source/import metadata refreshes and the exact module object remains sealed after reload.

Retained hostile tests cover both sides of the capture boundary. The original semantic-root suite attempts to replace the reconciler's captured upstream compiler with a forged generation carrying `stage=INVOICED_OR_AWARDED` and `settlement_target_cents=0`, replace its verifier with an always-true verifier, replace public compile functions, and widen external-acceptance/route class sets. The pre-import suite starts in a fresh child, imports the upstream funnel engine first, attempts ordinary assignment of its `compile_bundle`, `verify_bundle`, and `_make_core` exports before the reconciler exists, and only then imports/compiles/verifies the reconciler. Those replacements must fail before a forged generation can be sealed as trusted and before `DONE_ZERO_VALUE` / stronger acceptance can self-verify. Both root suites run under normal Python and `python -O`.

## Explicit non-claim

This is not a machine-strong sandbox against arbitrary same-interpreter or host takeover. Direct mutation of a module's backing `__dict__`, `sys.meta_path` surgery, custom loader execution, reflective mutation of function defaults/closures/code objects, installed-source replacement, debugger/frame surgery, interpreter replacement, or operating-system/process-boundary defeat are outside this ordinary module-rebinding boundary. Consumers needing resistance to those capabilities require a separately controlled interpreter/process boundary.

The cash boundary is unchanged: retained payment confirmations are not provider authentication; upstream `PAID` still resolves only to `VERIFY_PROVIDER_CASH`; all external-send, Muse-selection, invoice, provider/payment, receivable/accounting, and revenue-recognition authority remains hard false.
