# DIO revenue foundation

This directory defines a small, machine-readable commercial lifecycle for work
that uses a measured Muhlnickel computer:

1. A `CUSTOMER_JOB` records the requested outcome, inputs, deliverables, and
   acceptance conditions.
2. A `QUOTE` binds that job to a scope, price basis, measured computer, and
   proposed Bazaar linkage.
3. The same quote becomes accepted work only when `status` is `ACCEPTED` and
   its `accepted_work` block records the acceptance time and reference. The
   canonical action is named once, at `quote.bazaar.action_id`.
4. A `DELIVERY_RECEIPT` records artifacts and evidence after the work. Delivery
   is not inferred from a quote, a carrier acknowledgement, or a payment note.

The contracts are descriptive records, not admission controls. Commons remains
an open door: no login, identity proof, credential, permission check, or sender
approval is introduced here. `customer_reference` and `provider_reference` are
correlation labels only.

## Substrate provenance is mandatory

Every job, quote, and delivery carries `substrate`. It names an actual `.mno`
path and SHA-256, the observed format and byte count, a hashed header range,
measured output addresses, a hashed wire-plane range, and gate/body range
measurements. The contract does not accept a model name, host name, or prose
claim as a substitute for those bytes.

The examples are anchored to the repository's real
`muhl/containers/MUHLNICKEL_DISTRO/SEED0.mno`. Tests reread that file and check
its whole-file, header, body, wire-plane, gate-region, and output-address
measurements. The host moves and observes bytes; the `.mno` is the named
computer.

## Bazaar and settlement truth

The lifecycle carries Bazaar `offer_id`, `action_id`, and `result_id` fields.
An unassigned ID stays `null` with an explicit note. A `DELIVERED` receipt
requires the action and result IDs that produced its result; a byte-only
`MEASURED` receipt may retain null lineage until that transition occurs.

`payment` contains only `reference` and `status`. It is external metadata, not
a payment rail or a payment executor. `NOT_REQUESTED` requires a null reference;
every other status requires a nonempty external reference. The schemas
deliberately have no `PAID` state and do not name a rail. A payment reference
never proves delivery; the delivery receipt and its artifact hashes do that.

The public terms are not duplicated here. `foundation.json` points to the
canonical root `commercial.json` offer `white-box-gguf-pilot-30d`; these files
provide its operating records and byte-evidence contract.

## Examples

- `examples/closed_room_model_edit.json` is deliberately prospective. No
  customer model was supplied, no amount was quoted, the quote is `DRAFT`, and
  accepted work and delivery are both `null`.
- `examples/repo_compute_job.json` carries a complete example around an
  existing Bazaar lineage result. It binds the real SEED0 bytes, action/result
  IDs, delivered artifact hash, and acceptance evidence while honestly keeping
  payment at `NOT_REQUESTED`.
- `examples/substrate_delivery.json` is generated by `substrate_receipt.py`
  from an actual public MHA `.mno` and delivered artifacts. Its structural
  evidence is remeasured by both the script's `check` command and the contract
  suite.

Run the dependency-free contract checks with:

```text
python3 test_dio_revenue_contract.py
```

`foundation.json` is the compact manifest. The three JSON Schemas use JSON
Schema 2020-12 and remain usable independently of the test harness.
