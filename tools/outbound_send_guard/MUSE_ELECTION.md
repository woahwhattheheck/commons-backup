# Muse outbound election receipt v1

The fleet already has buyer-scope dedupe, provider-capability leases, turn-generation leases, and owner-policy gates. Those primitives do not answer a different coordination question: **which one of many near-simultaneous seats is allowed to carry one exact outbound candidate forward?**

The owner-designated arbiter is the Muse assistant in Slack. Before an email-like prospect publication, a claimant sends Muse an exact election request. The live orchestration layer may treat Muse's actual connector-read response as coordination input, but this repository's **v1 JSON compiler cannot authenticate Slack provenance** and therefore no longer certifies a positive election prerequisite from caller-supplied evidence.

`muse_election.py` remains useful for deterministic request construction and fail-closed observation validation. It is not a sender and it is not a Slack authenticator.

## Pinned route

v1 pins the observed workspace route used by the fleet:

- Muse Slack user: `U0C0TKRTQHZ`
- Muse DM conversation: `D0C1U7TUZEC`
- response deadline: 10 minutes after request construction
- observation freshness: 10 minutes after Muse's reported response

A route/identity change requires a code review and versioned policy update; callers may not override these values at runtime.

## Exact candidate

An election candidate binds six fields:

- `buyer_scope_sha256`
- `offer_scope_sha256`
- `intent_sha256`
- `body_sha256`
- `claimant`
- `operation_id`

Changing the body, offer, buyer, intent, claimant, or operation produces a different candidate digest. A response for one digest cannot be composed with another candidate.

## Protocol

Prepare a request:

```bash
python -m tools.outbound_send_guard.muse_election prepare \
  --buyer-scope-sha256 "$BUYER_SHA" \
  --offer-scope-sha256 "$OFFER_SHA" \
  --intent-sha256 "$INTENT_SHA" \
  --body-sha256 "$BODY_SHA" \
  --claimant Z-Anvil \
  --operation-id COMMONS-MUSE-OUTBOUND-ELECTION-ZANV-20260914 \
  --request-id zanv-20260914-0001 \
  --requested-at 2026-09-15T00:30:00Z
```

Send the emitted `message` **unchanged** to the pinned Muse DM. Muse's wire response is still:

```text
SELECTED <request_id> <candidate_sha256>
```

or:

```text
NOT_SELECTED <request_id> <candidate_sha256>
```

A trusted orchestration layer should read the DM through the Slack connector. A local evidence object can record the observed request/response for auditing:

```json
{
  "channel_id": "D0C1U7TUZEC",
  "request_message_ts": "1789432201.000001",
  "request_author_user_id": "U0CLAIMANT",
  "request_text": "<exact emitted message>",
  "response_message_ts": "1789432240.000001",
  "response_author_user_id": "U0C0TKRTQHZ",
  "response_text": "SELECTED zanv-20260914-0001 <candidate_sha256>"
}
```

Compile an observation only with a complete prior-election ledger for this publication path:

```bash
python -m tools.outbound_send_guard.muse_election compile \
  --request request.json \
  --evidence evidence.json \
  --prior-ledger prior-election-receipts.json \
  --ledger-complete \
  --observed-at 2026-09-15T00:31:00Z
```

The v1 compiler intentionally exits non-zero for compiled observations because v1 has no provider-authenticated provenance carrier and therefore cannot satisfy the positive election prerequisite.

## Provenance fence

A syntactically perfect local JSON snapshot is **not proof that Slack emitted those messages**. In particular, the following fields are public identifiers/data and are trivial for a caller to copy into a file:

- the pinned Muse DM ID;
- the pinned Muse user ID;
- plausible Slack timestamp strings;
- the request text generated by this module;
- `SELECTED <request_id> <candidate_sha256>`.

Therefore a v1 observation whose response text says `SELECTED` receives:

- `outcome=SELECTED` — what the caller-supplied observation reports;
- `decision=HOLD`;
- reason `SLACK_EVIDENCE_PROVENANCE_UNVERIFIED`;
- `muse_selected=false`;
- `election_prerequisite_satisfied=false`.

`verify_receipt()` also rejects legacy v1 receipts that claim `MUSE_SELECTED` / `muse_selected=true`, even when the caller recomputes the receipt digest. A hash over caller-authored bytes is an integrity label, not provider authentication.

This is deliberately fail-closed. A future positive machine-verifiable path must introduce a **versioned, independently authenticated provider/harness attestation**. Do not add a caller-settable `authenticated=true`, arbitrary evidence digest, or locally generated signature without an external trust root; those would simply recreate self-election under a different field name.

## Other fail-closed holds

The compiler also holds when any of these are true, among others:

- Muse is reported as `NOT_SELECTED` or the response does not use the exact response binding;
- wrong DM or wrong responder identity;
- response appears self-authored;
- request text differs from the compiled request;
- request/response ordering is impossible;
- response is reported after the ten-minute election window;
- selected observation is stale at compilation time;
- response echoes another request id or candidate digest;
- the prior-election ledger is incomplete/invalid;
- the same request, response, or evidence was already consumed by a prior valid v1 HOLD receipt.

Malformed/tampered request artifacts are invalid and raise instead of degrading into an apparent policy decision.

## Authority ceiling

A valid v1 receipt is an **audit/coordination observation only**. It never proves the positive Muse prerequisite and it never means:

- an email was sent;
- a recipient consented;
- an owner-policy decision was satisfied;
- buyer/contact dedupe is complete;
- provider capability is held;
- a payment or reply exists.

Both `external_send_authorized` and `side_effects_authorized` are always `false`. Any actual outbound carrier must still satisfy the live Muse arbitration rule in the trusted orchestration layer plus buyer/contact census, owner-policy gates when applicable, provider/turn lease, and fresh transport-side checks.

## Scope relationship to #14468

Publication-key collision semantics, multi-event snapshot/conflicting-winner/later-revocation behavior, and outbound-lease public identity/commitment binding remain that lane's scope.
