# Swarm Telemetry

Swarm Telemetry is a passive standard-library integration for collecting source events, storing them in SQLite, reporting available activity and resource totals, and deriving useful notifications. It does not authorize or dispatch work. Shared policy is in [SWARM_TELEMETRY.md](../../ground/SWARM_TELEMETRY.md) and [SWARM_THROUGHPUT_POLICY.md](../../ground/SWARM_THROUGHPUT_POLICY.md).

Events retain `event_id`, `source`, `source_id`, `occurred_at`, `observed_at`, `event_type`, `peer_id`, `session_id`, `agent_id`, `parent_agent_id`, `provider`, `model`, `harness`, `work_id`, `operation_id`, `status`, `summary`, `url`, `metrics` and `metadata`. Unknown fields remain unavailable. Source metrics may include input, output and cached tokens and provider cost, with observed, declared or estimated basis retained. Collection does not imply complete coverage of every provider or harness.

Snapshot and metric usage totals remain `null` until at least one session supplies that metric; a supplied numeric zero remains zero. `usage.metric_sessions` counts reporting sessions for each token or cost field, and `usage.metric_coverage` divides each count by the recorded session total (`null` when no sessions are recorded). These describe the collected records, not full provider coverage. The existing overall `accounting_coverage` continues to count sessions with any retained usage field.

`notifications_for_events(events)` returns deterministic notification dictionaries with `notification_id`, `event_id`, `work_id`, `type`, `severity`, `title`, `body`, `occurred_at`, `source_refs`, `audience`, `supersedes`, `status` and `metadata`. It accepts canonical `event_type` and `summary`, as well as notification-oriented `type`, `title` and `body`. Original source IDs take precedence over mirror-local event IDs. A collector should carry `original_event_id` in the event or metadata when mirroring. `audience` supplies `peers`, `channels`, `work_refs` and optional `owner_attention`; `peer_id`, `work_id` and source URLs also populate the affected audience and source references.

The baseline supports merge/merged/pr_merged, artifact/artifact_published, result/result_available, dependency_change/dependency_changed, rate_limit/rate_limited, service_recovery/service_recovered, owner_instruction, handoff, request_answer/explicit_request_answer, renewal_imminent, signature_needed, money_commitment, urgent, blocker_resolved and resolution event types. Hyphens are normalized to underscores. An adapter can supply the same explicit kind in `metadata.notification_type` when its canonical event type is generic. The baseline does not infer an owner's instruction or a merge from message prose. Unknown kinds produce no notification. A `money_commitment` marked `metadata.authorized_token_usage: true` or `metadata.commitment_scope: authorized_token_usage` produces no new commitment notice. Signatures, new commitments and urgent events identify owner attention; they do not stop work. A supplied owner-attention flag on an ordinary event does not create owner email attention.

`resolves_event_ids` identifies prior source event IDs; `supersedes` identifies prior notification IDs. Either may appear at the event root or in metadata. The resolving update lists the prior notification IDs and marks originals present in the same batch resolved. The durable delivery/store layer carries those changes across batches. No notification acknowledgment is required.

Read stored notices through `get_notifications` or `/api/telemetry/notifications`. Both accept `limit`, `cursor`, `q`, `source`, `provider` and `harness`; the latter three match those fields when present in a stored notice. Continue with the returned `next_cursor` while `has_more` is true, keeping the same filters. `q` searches stored notification content. Exhausting a page sequence reports `result_complete: true` for that query, while `corpus_complete` remains false because collected history can still be incomplete.

Read a specific work history with `get_work_context` or `/api/telemetry/work?work_id=ID`, and an operation history with `trace_operation` or `/api/telemetry/operation?operation_id=ID`. Both forward `cursor`, `limit`, `order` and the event filters to the retained event store. Use the returned `next_cursor` while `has_more` is true, keeping the work or operation identity, other filters and `order` unchanged. `order=desc` traverses newest events first; `q` matches event summaries. Without `work_id`, the work overview accepts `limit` (default and maximum 1,000) and an opaque string `cursor`. Follow its `next_cursor` while `has_more` is true to reach every recorded work item. Work pages sort by latest occurrence time, then work identity, and retain the first page's `through_event_cursor`; newly inserted events appear on a fresh traversal. Existing event metadata can still be reconciled. `result_complete` describes this bounded listing, while `corpus_complete` remains false. Work-list cursors and integer per-work event cursors are distinct.

`enrich_available(notification, answer)` accepts an already available optional Jev answer and adds it under `metadata.optional_context`. It initiates no network request. It preserves baseline identity, severity, audience and resolution. Separate enrichment integrations can run asynchronously; missing enrichment does not delay ingest, summaries or delivery.

`Outbox(path, redactor=redact)` is an optional single-writer JSON outbox for adapters that do not use the main SQLite notification store. `enqueue(notifications)` persists redacted notifications. `deliver(dispatch, readback=None)` calls an existing service adapter with a redacted notification. `dispatch` returns a mapping with `status: sent`, `failed` or `uncertain` and actual provider receipt fields. A definite `failed` result may retry. Exceptions, unexpected statuses and interrupted sends become `uncertain`. The optional `readback(notification, receipt)` must return `sent`, `not_sent` or `uncertain`; only `not_sent` permits another dispatch. An inconclusive or failed readback retains the original delivery receipt for the next attempt and records its result separately in `last_readback`. Every retry retains the same notification ID. Use the root store's notification delivery state when available; do not operate two outboxes against the same destinations.

The caller owns audience expansion and multi-destination service delivery, including per-destination provider idempotency and readback. It must not report `sent` until every requested destination has a confirmed result; partial sends retain destination receipts for readback. The module does not route providers or obtain credentials. Internal Slack and owner email adapters use the existing shared service road and its actual authorization. Owner email attention is limited to signatures, new money commitments outside existing authorization, or urgent items. Normal token usage remains authorized.

Complete source envelopes enter encrypted custody before operational projection and delivery redaction. The built-in recursive `redact` scrubs labelled secret fields and common secret formats from operational records. An existing vault-aware redactor can be supplied to the optional outbox. Raw source envelopes stay private and retrievable by their stable custody references. Direct shared vault access remains available to every current and future peer; telemetry records no new admission, credential grant, review, mandatory claim or execution gate.

Run on real available records and read the exit status and output. No new package dependency, fixture, test suite or workflow is needed. The runner's documented commands are the entry point for collection, summaries and optional delivery.

Run `python -B -m integrations.swarm_telemetry serve --state PATH --config CONFIG.json --port 8893` from the repository root. The dashboard is `/`; `/api/telemetry/health` reports each live collector thread and source recovery state. Its `collector_progress` map retains the latest returned result and observation time for each reader in the current server process, including the independent census, discovery, inventory and local passes. Readers that have not returned are absent; collector-pass times do not replace source timestamps or establish complete source history. `collect` advances discovery, native census, machine history, Slack, GitHub, connected services and local transcripts once; `--local-only` advances local transcripts only. Readers keep provider cursors, native job IDs and full historical coverage in the same private state directory. Provider page budgets and ingest batches are resumable work quanta; unread pages remain pending and corpus completeness remains false until traversal finishes.

Reader health keeps collection coverage and native handoffs distinct. For GitHub, `pending` is the collector's `pending_selectors`: incomplete coverage rows, including unresolved templates, discovery aliases and account-discovery recovery. It is not a count of executable requests or unique queue entries. `pending_native_jobs` reports the existing native handoff count for every reader; Slack and service readers continue to use that count for `pending` as well. The `/source-jobs` interface is unchanged. A successful read or zero native jobs does not establish complete coverage or resolve account-binding and account-discovery failures.

Installed native connectors can supply exact responses through the open receipt bridge. Read `/api/telemetry/source-jobs?reader=slack` or `reader=services`; `limit` and `cursor` paginate the job list, with `total_jobs` and `next_cursor`. Call the job's installed `tool_name` using its complete `args` and existing `account_ref`, then POST the untouched response to `/api/telemetry/source-response` as `{"job_id":ID,"reader":READER,"arguments":ARGS,"tool_name":TOOL,"account_ref":ACCOUNT,"service":SERVICE,"payload":COMPLETE_RESULT}`. The response is sealed before acknowledgment, its source reference is returned, and the corresponding reader wakes to traverse continuation pages and descendants. Receipt request arguments protect cursor identity. This queue records missing source reads and creates no work assignment or access grant. A compatible existing tool gateway may be configured as `native_connector_gateway`; otherwise installed connector calls run in their native host and forward their exact receipts.

`source_ingest_batch_events` defaults to 128 (maximum 1000). Each finite batch commits its original encrypted envelopes and operational projections before reader cursors advance. Recovery replays use stable event identities. Diagnostic storage failures remain visible in the runtime health response and cannot terminate another reader. After a successful collection, the runner retires only its exact prior `collection_only` / `pending_recovery` diagnostic from current coverage, using the attempt's captured identity and observation time. The existing reader-health record retains `last_collection_error` with the original diagnostic, attempt start and recovery time; fresh source-engine fields and source completeness remain unchanged. Newer failures and storage/busy/recovery deferrals retain their pending state. Source coverage includes discovered scopes, descendant jobs, pages read, unread regions and provider recovery paths; discovery totals are separate from collected-history totals.

An existing connector host can import `collectNativePass` or `runNativeCollector` from `native_host.mjs`. Supply its authenticated `readPage` binding, which returns `{payload: UNTOUCHED_NATIVE_RESULT, account_ref: ACTUAL_BOUND_REFERENCE, binding_evidence: PROVIDER_IDENTITY_REFERENCE}`. The binding resolves the requested account using the existing direct shared credential facility or an account selector. A default connected account does not represent all other accounts of the same service. This adapter traverses the entire pending job list, forwards full responses directly to encrypted custody, and keeps failed or unmatched account reads pending. Its concurrency and poll interval govern collector work only. The host owns its normal lifecycle; importing the module does not install or launch a persistent service.

When the existing HTTP gateway already has concrete source readers configured through `source_reader_factory`, use `createGatewayReader` from the same module as the native host's `readPage`. It checks `/v1/tools` for the exact advertised account/service binding before sending a selected call, so older gateways and unbound accounts remain pending without a provider call. Provider arguments stay separate from `account_ref` and `service`; the returned payload retains the complete HTTP/native envelope and its actual binding evidence. Each read uses a fresh operation ID; a direct caller may supply `operation_id` to resume the same journaled read. Binding configuration, provider credentials and host lifecycle remain with the existing host.

```js
import {collectNativePass, createGatewayReader} from './native_host.mjs';
const readPage=createGatewayReader({gatewayURL:'http://127.0.0.1:8878'});
const result=await collectNativePass({baseURL:'http://127.0.0.1:8893',readPage});
```

Each native pass honors a job's recorded `next_attempt_epoch` (Slack) and `retry_at_epoch` (connected services) when they are valid future timestamps. If both fields are present, the later timestamp applies. Deferred source reads remain in the reader queue; due jobs continue immediately. The pass reports `deferred_jobs` and the earliest deferred `next_attempt_epoch` alongside `considered` and `captured`, so a source retry or live-tail interval is visible without repeating the connector call. These timestamps govern source collection only and never delay swarm execution.

The shared exact-source key reference is `telemetry/source-custody-key`. Peers retrieve it directly through the existing shared credential facility; the Windows storage target is a local implementation detail. Snapshots use a five-second cache and reuse the last completed snapshot while another reader refreshes it. Ingest never waits for a dashboard refresh. `coverage_page` identifies pagination of the snapshot's source list; the source endpoint provides continuation cursors for every remaining partition.

The human dashboard loads `/api/telemetry/summary`, also available as the `get_dashboard_summary` agent tool. A cold request immediately reports `summary_ready: false` with HTTP 202 while a background read prepares the full service totals. Later reads reuse the last completed summary during refresh. No preparing response presents unknown counts as zero. Detailed source groups use `/api/telemetry/source-groups?limit=100&cursor=CURSOR`; original partition IDs and the full snapshot API remain available. Older service projection metadata is repaired from retained coverage payloads when at least 1 GiB of disk headroom is available. Below that floor, the summary derives service names directly from those payloads without rewriting the database.

`python -B -m integrations.swarm_telemetry query --state PATH --tool get_dashboard_summary` computes the completed summary in the foreground before the one-shot process exits. The long-lived HTTP and MCP server keeps its asynchronous cached summary behavior.

The coverage index backfills retained partitions once per database upgrade. Its completion marker commits in the same transaction as the backfill; later opens reuse the index without reparsing coverage payloads. Existing coverage triggers maintain subsequent inserts, replacements and deletions. Service-name projection recovery remains independent of this bootstrap.

Database contexts in the event store and encrypted source custody close their SQLite connections after the existing transaction commit or rollback. Repeated reads and capture passes release their database handles immediately, without waiting for Python garbage collection. Direct connection callers retain the normal SQLite connection API.

Service summaries aggregate repeated account, harness, status and completion groups through the existing covering index before transferring metadata into Python. Every recorded partition still contributes to counts and freshness; the normal query needs no temporary grouping file. The low-disk legacy projection recovery path continues streaming individual rows.

Transcript history uses configurable `transcript_batch_files`, `transcript_batch_bytes` and `transcript_batch_records` collection quanta; defaults are eight files, 1 MiB and 256 records. Byte offsets and session/provider/model/usage context survive each committed batch. A partial or oversized record remains at its original offset with explicit pending coverage. The machine activity collector independently retains exact file ranges in source custody. Collector batches limit memory used by a collection turn; they neither sample history nor limit swarm work.

Full-source collectors can also POST their complete source envelopes as an events array to /api/telemetry/source-events. The response reports durable:true only after ciphertext and projections commit. This source-collection path is independent of the optional asynchronous work-observation queue. Exact event_id lookups and source/cursor indexes keep source-receipt readback bounded while historical ingestion runs.

Native application lifecycle data is supplied by an available host caller. The configured `native_runtime_path` contains the latest actual native API snapshot and its original `observed_at` timestamp; the 15-second census reader rereads this file and never substitutes its own fetch time for that source timestamp. This Python runtime has no built-in native application API refresh producer. A visible external host automation can be described by `native_refresh_producer` with its `id`, `kind`, `configured`, `status`, `interval_seconds` and registration time. Census reports this configuration separately from verified scheduled source reads. Registration alone does not freshen a session or establish successful scheduled collection. `native_host.mjs` advances connector source jobs and does not call the native application session API. The host must retain each complete native response in encrypted custody, then replace the snapshot metadata using its actual read time. Process census and other provider reads continue independently.

Native session state expires after `stale_after_seconds` (900 seconds by default). Stale executing/waiting states become declarations or unknown state, and source coverage becomes `pending_host_refresh`; the separate `native_app_sessions:refresh-producer` partition records `host_caller_required` or `external_host_configured` with its descriptor and pending execution evidence. Native snapshot rows and every prior source reference remain retained. The current native chat listing accepts at most 50 non-pinned rows plus all pinned rows, so this snapshot retains an explicit historical enumeration gap; archived and transcript source traversal have their own cursors. A missing host producer cannot make old execution counts current, and requires no peer admission or credential grant.

Provider event census resumes each Gemini/Grok stream from the cursor retained in the existing SQLite census state. A page-budget boundary or later read failure preserves the last successful page and its outstanding request identities; the next pass, including after a runner restart, continues from that cursor. Inspections rotate through least-recently inspected requests and remove requests when a terminal event or inspection arrives. The checkpoint contains only cursor and request metadata, with no provider message or result bodies. Direct callers of `collect_census` pass its returned `state` into the next call. Page-budget and inspection gaps remain explicit partial coverage; this does not establish full historical source custody or start provider work.

### Passive remote custody of encrypted source records

`python -m integrations.swarm_telemetry.remote_custody` snapshots the exact encrypted `source_records` into a private SQLite journal and prepares resumable chunks for an already-connected Google Drive account and folder. Use a stable operation ID across retries. The module uses the Python 3.11+ standard library and requires no encryption keys or decryption. Keep the source database, journal, downloaded ciphertext, destination configuration, and keys private; the commands below contain placeholders only. It does not provision providers, purchase capacity, or authorize paid usage; use an existing no-charge route.

```sh
python -m integrations.swarm_telemetry.remote_custody prepare --source-db PRIVATE-source.sqlite3 --journal PRIVATE-custody.sqlite3 --operation-id OPERATION_ID --account-ref ACCOUNT_REF --folder-id EXISTING_FOLDER_ID --chunk-bytes 4194304
python -m integrations.swarm_telemetry.remote_custody jobs --journal PRIVATE-custody.sqlite3 --limit 50 --cursor 0
```

If storage fails during initial journal creation, retry the same `prepare` command after restoring storage. The journal filename is published only after its schema and operation binding are complete. Existing journals are never replaced. Preserve any incomplete journal created by an older version and choose a new journal path.

`jobs` emits connector handoffs as `{object_id, action, tool_name, args}` plus `next_cursor`; execute them through the existing authenticated Drive connector. Use one native caller per journal and execute each emitted batch before requesting another. Traverse the returned cursors to finish a finite pass over the full operation snapshot. This traversal does not sample records. Complete each object's deterministic-name search before uploading or retrying an upload, then record the search result with every matching file ID. A completed search with no matches is valid: omit `--file-id` and retain `--complete`. The custody handoffs do not dispatch or throttle other work, schedule activity, or introduce peer-admission, approval, or acknowledgement gates.

```sh
python -m integrations.swarm_telemetry.remote_custody record-search --journal PRIVATE-custody.sqlite3 --object-id OBJECT_ID --file-id DRIVE_FILE_ID --complete
python -m integrations.swarm_telemetry.remote_custody record-search --journal PRIVATE-custody.sqlite3 --object-id OBJECT_ID --complete
python -m integrations.swarm_telemetry.remote_custody record-upload --journal PRIVATE-custody.sqlite3 --object-id OBJECT_ID --file-id DRIVE_FILE_ID
python -m integrations.swarm_telemetry.remote_custody record-readback --journal PRIVATE-custody.sqlite3 --object-id OBJECT_ID --file-id DRIVE_FILE_ID --download /private/downloaded-object
python -m integrations.swarm_telemetry.remote_custody status --journal PRIVATE-custody.sqlite3
```

An uploaded object remains **pending** until its downloaded bytes equal the expected bytes. The journal records **confirmed** copies only after that readback. Resume with the same journal and operation ID, performing the deterministic-name search before any upload retry. Each prepared operation is a fixed snapshot; later source records require a new operation and journal. Drive filenames are reconciliation references, not atomic exactly-once keys. After every chunk is confirmed, the operation manifest is prepared as JSONL with full record metadata, chunk hashes, and provider locations. The manifest itself must be uploaded and pass byte-equal readback before the operation has a confirmed remote manifest.

Recovery starts with the downloaded remote manifest and does not require the custody journal. `restore-jobs` emits native fetch handoffs for its referenced chunks. Supply their actual downloaded absolute paths in a private JSON mapping keyed by provider file ID or opaque filename. `restore` reconstructs encrypted `source_records` in a new SQLite database from the manifest and chunks; it preserves the original source records and requires no decryption key. When a trusted manifest digest is available, pass it with `--expected-manifest-sha256`.

```sh
python -m integrations.swarm_telemetry.remote_custody restore-jobs --manifest /private/remote-manifest.jsonl
python -m integrations.swarm_telemetry.remote_custody restore --manifest /private/remote-manifest.jsonl --downloads /private/downloads.json --output-db /private/NEW-source.sqlite3 --expected-manifest-sha256 EXPECTED_MANIFEST_SHA256
```

If the existing connected account or storage folder is unavailable, retain the local records and journal and report the specific missing route. Upload receipts alone do not establish confirmed custody. This workflow performs no local pruning, deletion, or cutover.

#### Long-term archives with a compact index

The `archive-*` commands retain a metadata-only private index across source snapshots. Adjacent encrypted record ranges are packed into content-addressed chunks; every source reference, IV, MAC, key reference, and segment offset stays separately recorded. Confirmed chunks are reused by content across operations. Record metadata and captured table-state versions are also deduplicated. The existing single-snapshot commands and confirmed v1 copies remain usable.

```sh
python -m integrations.swarm_telemetry.remote_custody archive-import-v1 --index /private/archive.sqlite3 --journal /private/confirmed-v1.sqlite3
python -m integrations.swarm_telemetry.remote_custody archive-prepare --source-db /private/source.sqlite3 --index /private/archive.sqlite3 --operation-id OPERATION_ID --account-ref ACCOUNT_REF --folder-id EXISTING_FOLDER_ID --chunk-bytes 4194304
python -m integrations.swarm_telemetry.remote_custody archive-jobs --index /private/archive.sqlite3 --operation-id OPERATION_ID --limit 50 --cursor 0
python -m integrations.swarm_telemetry.remote_custody archive-status --index /private/archive.sqlite3 --operation-id OPERATION_ID
```

Each preparation reads a complete SQLite snapshot. It retains every encrypted source record and the present checkpoint, coverage, cursor, and runtime-state tables. Use repeated `--state-table TABLE` arguments for other complete tables, including events or sessions. Table absence, empty tables, and unfinished source coverage remain explicit. A complete archive snapshot does not mean every provider history has been collected.

The native caller consumes each emitted handoff batch, recording searches, uploads, failures, and downloaded-byte readback through the corresponding `archive-record-*` commands. One reusable staging slot bounds local ciphertext staging to a chunk; uncertain uploads retain their bytes until reconciled. A batch offers at most one upload for that slot. Continue with the returned cursor, including a return to cursor zero while remaining uploads wait for readback. New uploads reread the original source ranges and require their captured hashes to match. Changed or missing source bytes remain pending. Original records and collector cursors are never pruned, advanced, or rewritten by this workflow.

Compression is lossless and used only when the encoded object is smaller. Already-encrypted data commonly remains raw; compressed manifests retain exact table values and recovery metadata. Logical and stored byte counts are reported separately. Provider capacity remains unknown unless an actual provider quota observation supplies it; a successful small upload does not establish unlimited capacity. `archive-capacity --index INDEX --receipt PRIVATE_JSON` accepts observed `limit_bytes`, `used_bytes`, and `available_bytes` with `observed_at` and `basis`; unavailable values remain null.

Each operation has its own remotely confirmed recovery manifest. Fetch it through the existing Drive binding, use `archive-restore-jobs` for its distinct chunk downloads, and run `archive-restore` with the downloaded manifest and private file mapping to create a new database. Recovery does not require the original source or local archive index. Preserve the manifest digest through the existing private handoff. `archive-rebuild-index` reconstructs a new confirmed index from those same downloaded objects, without the original index or source database.

```sh
python -m integrations.swarm_telemetry.remote_custody archive-restore-jobs --manifest /private/manifest.bin --expected-manifest-sha256 MANIFEST_SHA256
python -m integrations.swarm_telemetry.remote_custody archive-restore --manifest /private/manifest.bin --downloads /private/downloads.json --output-db /private/NEW-source.sqlite3 --expected-manifest-sha256 MANIFEST_SHA256
python -m integrations.swarm_telemetry.remote_custody archive-rebuild-index --index /private/NEW-index.sqlite3 --manifest /private/manifest.bin --downloads /private/downloads.json --manifest-file-id DRIVE_MANIFEST_ID --account-ref ACCOUNT_REF --folder-id EXISTING_FOLDER_ID --expected-manifest-sha256 MANIFEST_SHA256
```

Recovery rebuilds declared columns, types, primary keys, and exact typed rows. Original SQL descriptions are retained privately but are not executed; source indexes, triggers, and defaults are not recreated from manifest SQL. Excluded internal SQLite bookkeeping, such as `sqlite_sequence`, is explicitly named in `source_scope`.
